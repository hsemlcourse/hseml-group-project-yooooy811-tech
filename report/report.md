## 1. Введение и постановка задачи

- **Цель проекта:** Суть проекта в том, чтобы предсказать будет ли доставлен онлайн-заказ вовремя или с задержкой. Это нужно для экономии ресурсов крупных компаний, которые занимаются доставкой, т к с помощью моего проекта можно заранее найти проблемные заказы и принять меры.
- **Формулировка задачи:** Бинарная классификация (1-задержка, 0-вовремя).
- **Обоснование метрики качества:** F1-score. Ее преимущество в том, что она учитывает сколько задержек из тех, что назвала модель реальны, и сколько из всех реальных задержек модель назвала. Метрика высокая только тогда, когда модель не пропускает задержки и не выбирает их просто так.

---

## 2. Поиск и описание данных

- **Источник данных:** Датасет DataCo Smart Supply Chain нашли на Kaggle (ссылка: https://www.kaggle.com/datasets/shashwatwork/dataco-smart-supply-chain-for-big-data-analysis). Датасет нашла на Kaggle по ключевым словам. Он достаточно большой и у него много признаков, которые помогли бы точнее предсказать задержку. Также датасет основан на реальных данных. 
- **Описание датасета:**
  - Объём: 180 519 строк и 53 столбца
  - Описание признаков: Каждая строка в датасете это заказ, у которого есть признаки. У признаков есть несколько категорий: числовые (цена, скидка, плановое кол-во дней доставки и тп), текстовые (способ доставки, тип оплаты, рынок и тп.). Помимо признаков заказа есть дата заказа и отправки, а также персональные данные заказчиков. Распределение между задержками и прибывшими вовремя почти поровну.

## 3. Обработка и подготовка данных

- **Полная очистка:**
  - Пропуски: Пропуски обнаружены при помощи df.isnull().sum(), они были в колонке Customer Zipcode, но мы их никак не заполнили т к эта колонка не несла никакой ценности и была удалена. 
  - Дубликаты: Дубликаты проверяли при помощи df.duplicated().sum(), их не выявлено 
  - Выбросы: Выбросы были обнаружены при помощи графиков (боксплотов). В колонках Sales, Order Item Product Price, Order Profit Per Order мы обрезали выбросы по диапазону от 1 до 99 перцентилей. 
  - Типы данных: Даты были в виде текста, мы их привели к типу datetime при помощи pd.to_datetime() 
- **Работа с фичами:**
  - Исходное количество признаков: Изначально было 53 признака, но некоторые содержали в себе ответ, некоторые имели неважные для анализа данные, некоторые дублировали информацию из других колонок, некоторые несли в себе слишком много информации (Order City) и поэтому были удалены.
  - Новые фичи, feature engineering (какие созданы и зачем): Из 9 текстовых колонок (вроде названия регионов, типа доставки и тп) после One-Hot Encoding стало 100 числовых + 14 числовых изначальных -> стало 115 новых фич. 
- **Визуализации:**
  Есть графики распределения таргета, распределения числовых признаков, связь категориальных признаков с таргетом, матрица корреляций, боксплоты для поиска выбросов, важности признаков, PCA визуализации в 2d. 
- **Сплит данных:**
  - Стратегия разбиения (train/val/test), соотношение: 70%  это тренировочные данные, 15% для сравнения моделей, 15% для итогового тестирования. При помощи стратификации сделала так, чтобы во всех кусках было одинаковое соотношение задержек с доставленными вовремя (55% к 45%). 
  - Как избегали data leakage (если он мог возникнуть - временные ряды, утечка целевой и т.д.): Чтобы избежать data leakage я удалила колонки в которых был ответ (Delievery Status, Days for shipping(real)), не использовала колонку в которой была дата отправки заказа для фич, потому что на стадии оформления заказа мы не можем точно утверждать когда его отправят, настроила масштабирование только на обучающих данных.

## 4. Baseline-модель

- **Модель:** Я использовала логистическую регрессию (Logistic Regression) как простую модель для классификации, которая просто делила данные по прямой линии. Использовала масштабирование признаков, чтобы модель не думала ошибочно что заказ важен\неважен только из за количества товаров и цены.
- **Результаты:** Accuracy 0.72, F1 0.69, ROC AUC 0.74 на val. Для задержек recall был 0.56 (модель не угадывала много реальных задержек).
- **Цель:** Любая последующая модель должна быть лучше метрики F1 0.69

## 5. Эксперименты

Эксперимент 1. Сравнение моделей.
**Гипотеза** Деревья решений лучше справятся с поставленной задачей, чем линейные модели, т к зависимости между признаками заказа и статусом (задержка\вовремя) могут быть нелинейными (необзятально, чтобы с ценой\количеством росла вероятность задержки).
**Как проверялось** Я обучила 7 моделей, для каждой использовала значения по умолчанию : Logistic Regression, KNN (k=11), Decision Tree (глубина 10), Random Forest (100), Gradient Boosting (200), XGBoost(200), LightGBM (200).
**Результат** Лучшую метрику F1=0.75 показал Random Forest, худшую F1=0.69 показал KNN. Модели с деревьями были в диапазоне 0.71-0.75, что лучше линейных с 0.69. Гипотеза верна
Эксперимент 2. Подбор гиперпараметров через Optuna.
**Гипотеза** Предполагается, что автоматический подбор параметров улучшит результат.
**Как проверялось** Для лучших моделей Random Forest и XGBoost запустили Optuna на 30 итераций. Я перебирала следующие параметры: кол-во деревьев (100-500), глубину (3-10), скорость обучения (0.01-0.3), часть данных для каждого дерева, мин. размер листа
**Результат** XGBoost показал резкий скачок точности с 0.72 до 0.83. Для него лучшие параметры: 242 дерева, глубина 10, скорость 0.30. Random Forest снизился с 0.75 до 0.72. Гипотеза верна для XGBoost.  
Эксперимент 3. Ансамбли.
**Гипотеза** Используя несколько моделей в комбинации, мы получим результат лучше, чем используя одну модель. 
**Как проверялось** Собрали голосование из трех моделей (voting) + предсказания из трех моделей, пока четвертая учится на их ответах (stacking) из XGBoost, RF и LightGBM. 
**Результат** Voting 0.78, stacking 0.81, что оказалось хуже чем результат из эксперимента 2. Гипотеза не подтвердилась, т к когда одна модель лучше всех, остальные модели занижают результат среднего. 
Эксперимент 4. Уменьшение размерности.
**Гипотеза** Сократить количество (115) признаков без потери точности.
**Как проверялось** Я применила PCA и посмотрела сколько нужно компонентов для дисперсии 95%. Для наглядности визуализировала данные на графике 2д.
**Результат** 2 компоненты объясняют только 6.6% дисперсии, потому что данные слишком сложные для линейного сжатия. Для 95% нужно 82 компоненты из 115, т е сжатие очень мало экономит. Гипотеза не подтвердилась, и я работала с полным набором данных.

## 6. Финальная модель и интерпретируемость

- **Обоснование выбора финальной модели:** Я выбрала XGBoost т к она показала лучшую метрику F1 = 0.826. Также я пробовала stacking и он дал похожий результат 0.813, но он слишком затратный и сложный, чтобы его использовать вместо XGBoost. На тестовых данных XGBoost дала 0.829, значит модель не переобучилась.
- **Интерпретируемость:** Топ признаков: Days for shipment (scheduled), Shipping Mode_Standard Class, order_hour, Latitude, Longitude. Главным фактором задержки является запланированный срок доставки, т е если компания выделяет мало дней на доставку заказа,то возрастает риск задержки. Стандартный тип доставки чаще выдает задержки по сравнению с экспрессом. Также важно учитывать час оформления заказа, чем позже оформили - тем выше что заказ не успеют собрать вовремя. Еще важно обращать внимание на координаты региона, т к в удаленные пункты заказы доходят дольше.

## 7. Деплой

- **Интерфейс:** Был создан веб-интерфейс в Streamlit. Пользователь может выбирать нужные параметры через ползунки и списки на страничке. При нажатии кнопки "Предсказать" мы можем видеть придет ли заказ вовремя или задержится с процентом вероятности предсказания.

## 8. Заключение и выводы

- **Итоги:** Была обучена модель XGBoost которая может предсказать задержку доставки с F1 0.83 на тестовых данных. Изначально работала с логистической регресссией с F1 0.69. Сравнивала 7 моделей и проводила 4 эксперимента с лучшими из них, чтобы максимально улучшить XGBoost c 0.72 до 0.83 (при помощи подбора гиперпараметров через Optuna).
- **Ограничения:** Так как модель обучалась на данных только от одной компании со своей логистикой, для других компаний доставки будет затруднительно предсказывать задержку. Также у нас нет данных о погоде, праздниках, состояниях дорог которые могли бы улучшить точность вероятности задержки.
- **Возможные улучшения:** Можно добавить внешние данные (погода, дороги, календарь и тп) для повышения точности, попробовать нейросети, поработать с логистикой других компаний для достижения универсальности предсказания, сделать отдельные модели для разных рынков.
